# Prose scalars before capture joins

Classification: compiler/optimizer. The public prose grain is already one row per
content. The original plan carries prose through the capture join before computing
a small count; broad prose scanning remains necessary. Hypothesis: materializing
(content_id, count) before the join reduces payload and repeated computation while
preserving latest eligible capture selection. This does not reduce files scanned.

The registered `prose-mention-counts` case reproduces the reported memory/spill
failure. No private URL or request identifier appears in the case.

Acceptance: complete equal ordered results/types at a frozen production snapshot,
both execution orders, identical limits; conservative activation and adversarial
semantics tests. Stable remains unchanged. Production acceptance after review and
deployment must execute unchanged SQL through the experimental API.

## Implementation and correctness

`query/prose_scalar.py` owns the deliberately narrow compiler rule. It creates one
materialized CTE, projects only content ID and a computed match count, and replaces
the original prose source with that producer. There is no distinct-content rewrite:
input multiplicities are preserved. The original capture/prose eligibility join
still precedes latest-row selection. Positive-count filtering stays after it, so an
old positive page never substitutes for a newer nonmatching page. Content shared by
several URLs still counts separately for those URLs.

Conservative eligibility and installed-definition checks are documented in QUERY.md.
A one-row native regex validation uses TRY over a relation to avoid DuckDB constant
folding the invalid expression outside TRY and aborting the read transaction.
Adversarial tests cover missing prose, latest null/nonmatch, duplicate captures,
shared content, time/ID ties, word boundaries, empty results, aliases, source order,
unsupported syntax and the configuration-locked service in both execution modes.
A physical-plan test requires the CTE producer to project the scalar before joins.

## Frozen production-corpus evidence, 2026-09-11

Read-only diagnostic pod using deployed image 4167701 / DuckDB 1.5.5, with the
candidate compiler modules copied into that disposable pod only. Shared bench
`measure_pair` executes SQL generated by the actual rule and verifies installed
catalogue definitions in the same transaction. Each pair uses one frozen snapshot,
two threads, 256 MB spill, one initial execution and three ordinary warm executions.
These are ordinary execution timings, not EXPLAIN ANALYZE profiles. No scan or peak
memory counters are claimed. Deployment settings were not changed.

At 512 MB, baseline-first failed during initial execution (snapshot 107643).
Candidate-first returned 20 rows in 11.43 seconds and completed one warm repeat,
but failed on a later warm execution (snapshot 107652). Neither incomplete run is
an equivalence pass. **The rewrite does not reliably cure the 512 MB memory failure.**

Giving both variants 1 GB in the diagnostic pod allowed complete controlled pairs:

| Order / snapshot | Baseline warm median | Candidate warm median | Reduction |
| --- | ---: | ---: | ---: |
| Baseline first / 107658 | 1,181 ms | 942 ms | 20.3% |
| Candidate first / 107671 | 1,151 ms | 925 ms | 19.6% |

Both pairs returned exactly equal complete ordered results, column names and types
(20 rows), with every warm repeat also checked. Initial baseline/candidate times
were 11,232/972 ms and 1,346/9,863 ms respectively: cache/order effects dominate;
there is no claimed tenfold gain. These are measurements on today's corpus, not a
billion-content scaling guarantee. Broad prose scanning is unchanged.

### Actual query-service path

The unmodified submitted SQL was also executed through the candidate's actual
configuration-locked QueryService in the disposable reader pod at 512 MB, with
normal preparation, catalogue/regex checks, resource limits and result wrapper.
Experimental v6 reported `prose_scalar_before_capture_v1` and returned 20
untruncated rows in all three executions: 18.09, 2.65 and 12.62 seconds, snapshots
107679, 107681 and 107683. Stable v4 failed two of three attempts with OOM; its
successful middle execution took 18.24 seconds at snapshot 107692.
These advancing-snapshot observations verify service activation, not controlled
speedup/equality or a reliable failure-rate estimate. The production deployments
were untouched. The temporary pod was deleted after collecting aggregate evidence.

### Repeating the paired bench

With the existing production **reader** environment, run from `packages/periplus`:

```python
from dataclasses import replace
from pathlib import Path
from periplus.query.benchmarking import load_case, measure_pair, compare_reports
from periplus.query.prose_scalar import prose_scalar

case = load_case(Path('../../benchmarks/query/cases/prose-mention-counts'))
candidate = prose_scalar(case.sql)
assert candidate is not None
pair = measure_pair(
    case, replace(case, sql=candidate.sql), None,
    warm_runs=3, candidate_first=False, verify_scope=candidate,
    profile_warm_runs=False,
)
comparisons, failures = compare_reports(
    {'measurements': [pair['baseline']]},
    {'measurements': [pair['candidate']]},
)
assert not failures
print(comparisons)
```

Repeat with `candidate_first=True`. The ordinary deployment memory budget can fail;
use `PERIPLUS_DUCKDB_MEMORY_LIMIT=1GB` for **both** diagnostic variants to reproduce
the complete timing/equality pairs above. Do not change production settings to run
this comparison. Follow the shared bench protocol for access paths, safe failure
reporting and private artifact handling.
